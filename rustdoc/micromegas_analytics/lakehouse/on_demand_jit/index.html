Query-driven materialization of on-demand SQL views Query-driven materialization of on-demand SQL views (DDL views with no update_group).

A query over query_range fills and refreshes the partitions covering that range, so nothing is materialized for ranges nobody reads. The range is cut along the bucket ladder (see partition_ladder), each bucket’s freshness is probed with the view’s own authored count_src_query, and the stale ones are rewritten with its extract_query.

A bucket grows into a [Unit] that contains every partition row it intersects (an earlier query at a coarser rung, a promotion, or rows left by the daemon before a view was converted), so a write’s containment retire always replaces everything it overlaps and the verdict of a unit never depends on another unit.

Functions§

judge_unit
Covered when the unit has rows, every row was written with the view’s current schema, and the rows’ summed source_data_hash equals the count the probe returned. This is the maintenance daemon’s freshness rule (equality, summed), so a definition gets the same verdicts under either writer.
plan_units
Grows each planned bucket until it contains every row that intersects it, then coalesces the units that came to overlap. planned is ascending and non-overlapping. Rows are half-open against the unit (Aligned): SQL partitions touch at bucket edges, and a neighbor that merely touches is not absorbed.
promotion_targets
Picks the units to promote: covered, closed, exactly one planned bucket at the query’s rung (not grown), holding at least two rows that merge. Pure, like promotion_candidates.
update_on_demand_view
Brings an on-demand view up to date for query_range: sizes buckets from the range, probes each one, rewrites the stale ones, then promotes closed history to the range’s rung.
