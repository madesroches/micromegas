Organizing notebooks into folders

Three interactive mockups for issue #1159: letting users group screens (notebooks, log views, tables, metrics) into a folder hierarchy and find one quickly by name. Each mock reuses the app's current dark theme and component styling, is fully click-through (expand folders, search, move a screen via its ⋮ menu, preview the updated save dialog), and works against the same 13 fake screens so the three are easy to compare directly.

The three alternatives

Open each in its own tab and try the search box and the "Preview: Save dialog" button — behavior differs meaningfully between them.

A Sidebar tree explorer

A persistent, collapsible folder tree on the left (like VS Code's file explorer). Selecting a folder filters the main grid to its contents; an "All Screens" pin at the top shows everything flattened with a folder badge on each card.

Strong fit when
  • Hierarchy depth is real and worth seeing at a glance
  • Users will maintain the tree over time (rename, nest, reorganize)
Cost
  • Fixed sidebar width eats into card real estate
  • Most new UI surface of the three to build and test
Open mock →

B Breadcrumb explorer

No persistent sidebar. Folders and screens appear together as cards in the current directory (Google Drive-style); a breadcrumb trail at the top navigates back up. Search still flattens across the whole hierarchy.

Strong fit when
  • Screen names/thumbnails matter more than seeing the whole tree
  • Most users stay a folder or two deep, not deeply nested
Cost
  • No at-a-glance overview of the full hierarchy
  • Jumping between distant folders takes more clicks than a tree
Open mock →

C Grouped list, search-first

Keeps today's single scrolling list, but sections it by folder with collapsible headers. A prominent search box up top is the primary way to find something; typing flattens all groups into one filtered, highlighted result list.

Strong fit when
  • Folders are mostly a light label, not a deep structure
  • Search-by-name is how people will actually find screens day to day
Cost
  • One folder level only — no visual nesting for sub-subfolders
  • Many folders means many headers even when collapsed

Data model, all three alternatives: a single folder_path string column on screens (e.g. "team/dashboards", empty string for the root), per the issue's proposal — no separate folders table needed. Folders exist only as distinct path prefixes of at least one screen, except in A/B where "new (sub)folder" is offered as an explicit action — that needs either a placeholder/marker row or a lightweight folders table so an empty folder can persist before anything is saved into it. C never lets you create an empty folder, so it avoids that question entirely — folders there come into existence only when a screen names one.
Fake data only (13 screens across 8 folder paths, repeated identically in A/B/C). Screen-type icons and color tokens are copied from analytics-web-app/src/styles/globals.css and ScreensPage.tsx — nothing here is wired to the real API.
